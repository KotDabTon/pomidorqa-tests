# Как работать с репозиторием

## 1. Клонирование и установка

Если репозиторий ещё не склонирован:

```bash
git clone https://github.com/KotDabTon/pomidorqa-tests.git
cd pomidorqa-tests
npm install
npx playwright install chromium
```

Если репозиторий уже склонирован:

```bash
git checkout main
git pull origin main
npm install
```

## 2. Проверка проекта

Перед внесением изменений запустите тесты:

```bash
npm test
```

Проверьте линт:

```bash
npm run lint
```

Если тесты или линт падают, сначала определите причину существующей ошибки, чтобы не смешивать её со своими изменениями.

## 3. Создание ветки

Для новой задачи создайте отдельную ветку:

```bash
git checkout -b feature/<short-description>
```

Для исправления дефекта:

```bash
git checkout -b fix/<short-description>
```

Название ветки должно кратко описывать задачу.

## 4. Внесение изменений

Изменения должны соответствовать задаче и не затрагивать несвязанные части проекта.

Перед коммитом проверьте:

```bash
npm run lint
npm test
```

Если изменение относится только к одному уровню тестов, можно дополнительно запустить соответствующий набор:

```bash
npm run test:unit
npm run test:api
npm run test:e2e
```

## 5. Коммит

Используйте короткое описание изменения:

```bash
git add -A
git commit -m "test: добавить проверку отмены бронирования"
```

Примеры:

```text
test: добавить E2E-проверку
fix: исправить локатор
ci: обновить workflow
docs: обновить документацию
refactor: вынести общий helper
```

## 6. Pull Request

Отправьте ветку:

```bash
git push origin feature/<short-description>
```

Создайте Pull Request в `main`.

В описании PR укажите:

* что изменено;
* какие сценарии добавлены или исправлены;
* какие тесты запущены;
* результат линта;
* известные ограничения или дефекты, если они есть.

## 7. Требования к тестам

При добавлении автотестов соблюдайте структуру проекта:

* `tests/e2e` — пользовательские сценарии;
* `tests/api` — API-проверки;
* `tests/unit` — изолированные unit-проверки;
* `tests/pages` — Page Object'ы;
* `tests/helpers` — общие данные и вспомогательные функции.

Не размещайте локаторы непосредственно в spec-файлах, если для соответствующего экрана уже существует Page Object.

Регистрацию и подготовку тестовых данных выполняйте через helpers или API, если сама регистрация через UI не является предметом проверки.

Каждый тест должен быть независимым и использовать собственные тестовые данные.

## 8. Code Review

При ревью проверяются:

* корректность сценария;
* соответствие тестовой архитектуре;
* качество локаторов;
* читаемость теста;
* наличие `test.step` для значимых действий и проверок;
* отсутствие `sleep`, `force`, `.only` и необоснованных таймаутов;
* корректная подготовка и очистка данных;
* прохождение линта и тестов.

Ревью должно быть направлено на качество изменения, а не на форматирование ради форматирования.
