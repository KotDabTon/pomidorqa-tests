# PomidorQA Autotests

Автотесты учебного приложения **PomidorQA** на **Playwright + TypeScript**.

Репозиторий содержит тесты трёх уровней:

* **Unit** — проверка чистых функций без браузера и сети.
* **API** — проверка бизнес-логики через HTTP API локального mock-сервера.
* **E2E** — проверка пользовательских сценариев в браузере.

Проект организован как самостоятельный репозиторий с собственным CI и набором тестов.

---

## Происхождение кода

Проект — результат прохождения марафона «В AQA за 60 дней» (курс PomidorQA). По заданию курса материалы перенесены в личный репозиторий.

Написано мной — все E2E-сценарии (`tests/e2e/`), Page Object'ы (`tests/pages/`), хелперы (`tests/helpers/`), workflow в `.github/workflows/`.

Инфраструктура курса — `src/pyramid/`, `tests/unit/slots.spec.ts`, `tests/api/booking-api.spec.ts`, `playwright.config.ts`, `eslint.config.mjs`, `tsconfig.json`.

## Установка

Клонировать репозиторий и установить зависимости:

```bash
npm ci
```

Установить браузер Chromium для Playwright:

```bash
npx playwright install chromium
```

---

## Запуск тестов

### Все тесты

```bash
npm test
```

Запускает Unit, API и E2E тесты.

### Unit

```bash
npm run test:unit
```

### API

```bash
npm run test:api
```

### E2E

```bash
npm run test:e2e
```

### Линтер

```bash
npm run lint
```

### HTML-отчёт Playwright

```bash
npm run report
```

---

## Base URL

E2E-тесты используют базовый URL из переменной `POMIDORQA_BASE_URL`.

Если переменная не задана, используется значение из `playwright.config.ts`.

Для запуска против другого стенда можно задать переменную окружения:

```bash
POMIDORQA_BASE_URL=http://localhost:3000 npm run test:e2e
```

Для Git Bash:

```bash
POMIDORQA_BASE_URL=http://localhost:3000 npx playwright test --project=e2e
```

# Unit-тесты

## `tests/unit/slots.spec.ts`

Проверяет чистые функции из `src/pyramid/slots.ts`.

Покрывает:

* пересечение временных слотов;
* отсутствие пересечения;
* граничные случаи интервалов;
* форматирование времени слота;
* валидацию пароля.

Тесты не используют браузер, сеть или внешний сервис.

---

# API-тесты

## `tests/api/booking-api.spec.ts`

Проверяет бизнес-логику бронирования через локальный HTTP mock-сервер.

Покрываемые сценарии:

1. успешное бронирование свободного слота;
2. попытка забронировать собственный слот;
3. попытка забронировать прошедший слот;
4. бронирование несуществующего слота;
5. бронирование уже занятого слота;
6. гонка двух пользователей за один слот;
7. успешная регистрация нового пользователя;
8. регистрация с уже существующим email.

API-тесты не используют реальный UI.

---

# E2E-тесты

## `tests/e2e/booking-cancel.spec.ts`

Проверяет полный сценарий бронирования и отмены встречи.

Сценарий включает:

* создание участника через API;
* добавление навыка;
* добавление свободного слота;
* создание гостя;
* поиск участника;
* бронирование слота;
* проверку предстоящей встречи;
* отмену встречи;
* перезагрузку страницы;
* проверку сохранения результата;
* проверку отменённой встречи со стороны владельца слота;
* cleanup созданных пользователей.

---

## `tests/e2e/booking-flow.spec.ts`

Проверяет основной сценарий бронирования и конкурентную попытку забронировать один и тот же слот.

Используются отдельные BrowserContext для:

* владельца слота;
* первого гостя;
* второго гостя.

Проверяется:

* подготовка данных через API;
* отображение участника в каталоге;
* выбор одинакового свободного слота;
* успешное бронирование одним пользователем;
* ошибка второго бронирования;
* отображение результата бронирования.

---

## `tests/e2e/catalog-search-scope.spec.ts`

Проверяет область и правила поиска участников в каталоге.

Сценарии:

1. гость находит участника по уникальному навыку;
2. поиск показывает подходящего участника и исключает участника с другим навыком;
3. авторизованный пользователь не видит собственную карточку, а гость видит её.

Для разных пользователей используются отдельные BrowserContext.

---

## `tests/e2e/data-after-reg.spec.ts`

Проверяет сохранение пользовательских данных после регистрации.

Сценарии:

* имя пользователя сохраняется после перезагрузки;
* навык `can_help` добавляется и сохраняется;
* свободный слот на следующий день создаётся и отображается.

Регистрация и подготовка данных выполняются через API, а пользовательские изменения и проверки — через UI.

---

## `tests/e2e/login-error.spec.ts`

Проверяет негативные сценарии авторизации.

Сценарии:

* вход с неправильным паролем;
* вход с несуществующим email;
* одинаковое сообщение об ошибке для разных причин неуспешной авторизации.

Цель — проверить пользовательское поведение и отсутствие раскрытия лишней информации о существовании аккаунта.

---

## `tests/e2e/profile-flow.spec.ts`

Проверяет работу профиля пользователя.

Покрываются:

* сохранение имени;
* изменение часового пояса;
* сохранение Telegram;
* сохранение bio;
* добавление навыка;
* запрет добавления пустого навыка;
* разделение `can_help` и `want_to_learn`;
* отсутствие сохранения несохранённого имени после reload;
* сохранение нескольких полей одной операцией.

# Helpers

## `tests/helpers/user.ts`

Содержит общую работу с тестовыми пользователями:

* типы пользователя;
* фабрику тестовых данных;
* регистрацию через UI;

* удаление текущего тестового пользователя;
* cleanup нескольких пользователей.

Helper используется для подготовки данных и очистки окружения после тестов.

---

## `tests/helpers/booking.ts`

Содержит общую инфраструктуру для сценариев бронирования.

Основные элементы:

* `AppContext`;
* `createApp`;
* `closeApps`;
* `prepareHostParticipant`.

`prepareHostParticipant` подготавливает участника для теста:

* создаёт пользователя;
* добавляет навык;
* создаёт свободный слот.

Это позволяет не дублировать одинаковый Arrange-код в нескольких E2E-тестах.

# CI

## `.github/workflows/playwright.yml`

GitHub Actions workflow для автоматической проверки проекта.

Запускается:

* при `push` в ветку `main`;
* при открытии или обновлении pull request в `main`;
* вручную — кнопкой **Run workflow** во вкладке Actions.

Workflow выполняет:

1. запуск на Ubuntu;
2. установку Node.js;
3. `npm ci`;
4. установку Chromium для Playwright;
5. `npm run lint`;
6. запуск тестов;
7. сохранение Playwright HTML report как artifact;
8. отправку сводки о прогоне в Telegram (`scripts/notify-telegram.mjs`).

Workflow предназначен для автоматической проверки состояния проекта в GitHub Actions.

Уведомление в Telegram отправляется и при успехе, и при падении тестов (шаг помечен `continue-on-error`, поэтому отсутствие секретов не красит CI в красный). Для работы нужны репозиторные секреты `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`.

# Принципы тестов

Основная организация проекта:

```text
tests/e2e/       сценарии тестов
tests/helpers/   данные, регистрация и подготовка окружения
tests/pages/     локаторы и действия страниц
tests/api/       API-тесты
tests/unit/      Unit-тесты
src/pyramid/     вспомогательный код и mock API
```

Основные правила:

* тест описывает сценарий;
* Page Object содержит локаторы и действия;
* helper содержит подготовку данных;
* API используется для Arrange, если регистрация не является объектом проверки;
* проверки выполняются через `expect` в тесте;
* осмысленные действия и проверки оформляются через `test.step`;
* тесты используют уникальные данные;
* созданные пользователи и контексты очищаются после теста;
* не используются `waitForTimeout`, `force`, `.only` и `page.pause()`.

Подробнее правила проекта собраны в `CODEX.md`.

# Результат

Репозиторий предназначен для запуска и демонстрации набора автотестов PomidorQA с разделением на:

```text
Unit
  ↓
API
  ↓
E2E
  ↓
CI / GitHub Actions
```

Цель структуры — отделить подготовку данных, действия пользователя и проверки результата, сохраняя тесты независимыми и читаемыми.
